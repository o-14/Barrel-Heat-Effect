# MCM panel and weapon coverage - 2026-08-11

Build: `dist\GunHeatHaze-0.6.0-mcm.zip`

## Weapon coverage

`Config::IsWeaponAllowed` is:

```cpp
if (allowedWeapons_.contains(a_weapon->formID)) return true;   // explicit ini allowlist
return allowAllWeapons_ && a_weapon->IsGunWeapon();
```

and `TESObjectWEAP::IsGunWeapon()` is `weaponData.type.any(WEAPON_TYPE::kGun)`.

`WEAPON_TYPE` has exactly one ranged-firearm value - `kGun = 9`. The enum splits
hand-to-hand, swords, daggers, axes, maces, bows, staves, **gun**, grenade and mine. It
does **not** distinguish ballistic from energy.

So with `bAllowAllWeapons=1`:

| | included |
| --- | --- |
| Ballistic firearms, vanilla and modded | yes |
| **Laser, plasma, institute, gauss, cryo, flamer** | **yes - energy weapons are not excluded** |
| Miniguns and other heavy guns | yes |
| Melee, unarmed | no |
| Grenades, mines, thrown | no |

Nothing keyword-based or FormID-based is involved, which is why modded guns work with no
patching: a modded weapon is typed `kGun` like any other.

The confirmed attach path reinforces this - `EquippedWeaponData::fireNode` resolved to
`ProjectileNode` on every cycle, and that field is filled in by the engine for whatever
weapon is equipped, including its attached mods.

**If you want energy weapons excluded**, there is no switch for it today. It would need a
keyword check (`WeaponTypeLaser` / `WeaponTypePlasma` exist as vanilla keywords - see
`GunHeatHaze_Discovery_Report.md`), which is a small addition to `IsWeaponAllowed`. Worth
noting the opposite argument: a laser barrel heating up is at least as plausible as a
ballistic one, and vanilla energy weapons have no heat effect of their own.

## MCM panel

MCM is installed here as the F4SE-plugin build - `Data\F4SE\Plugins\mcm.dll`,
`Data\Scripts\MCM.pex`, `Data\Interface\MCM.swf`. It ships no `.esp`, which is why it
does not appear in `plugins.txt`.

### How the wiring works

MCM writes the player's choices to `Data\MCM\Settings\GunHeat.ini` as plain
`[Section] key=value`, deriving the section from the `id:Section` suffix in
`config.json`. That is the same format `GunHeat.ini` already uses, and the same
convention the other DLL-backed MCM mods here use (`BPR.ini`, `UneducatedShooter.ini`,
`WeaponFamiliarity.ini`).

So the ids were named to mirror the real config keys, and `Config::Load` now does:

```text
Data\F4SE\Plugins\GunHeat.ini        <- base settings
Data\MCM\Settings\GunHeat.ini        <- MCM overrides, applied on top if present
```

Consequences worth knowing:

- **No Papyrus dependency on MCM.** Nothing in our scripts calls the MCM API, so the
  build does not need `MCM.psc` to compile, and there is no hard requirement on MCM.
- **MCM is optional.** With MCM absent the overlay file simply does not exist and
  `GunHeat.ini` is used unchanged.
- **Edits apply on the next burst**, not on a save reload. `HazeManager::Attach` calls
  `Config::ReloadOverrides()` at the start of each heat cycle, and the Papyrus controller
  re-reads its curve values right after. One exception: a changed **visibility threshold**
  applies from the cycle after next, because the current cycle was already triggered
  against the old value.

### Controls

| Panel control | Writes | Default |
| --- | --- | --- |
| Heat intensity | `[Haze] fRefractionMaxStrength` | 0.20 |
| Heat per shot | `[Heat] fHeatPerShot` | 0.085 |
| Visibility threshold | `[Heat] fMinHeatToShow` | 0.18 |
| Fade in (seconds) | `[Heat] fFadeInSeconds` | 0.80 |
| Cool-down, short burst | `[Heat] fMinFadeOutSeconds` | 8.0 |
| Cool-down, fully hot | `[Heat] fMaxFadeOutSeconds` | 14.0 |
| All firearms | `[Weapons] bAllowAllWeapons` | on |
| Scale heat by caliber | `[CaliberScaling] bEnabled` | on |
| Debug logging | `[Debug] bDebugLogging` | **off** |

### One trap the help text calls out

**"Cool-down, short burst" is also the cooling rate of a cold barrel.** Heat decays at
`1 / fadeOutSeconds`, and `fadeOutSeconds` scales from min to max with peak heat, so the
minimum governs how fast a barrel that has barely heated loses it. Setting it low makes
heat hard to build at all - that is exactly the bug that made 1030 logged shots produce
nothing back in `0.3.1`, where it was `2.0` and decay outran a realistic fire rate.

The slider floor is 2.0 and the help text warns that below roughly 4 seconds sustained
fire may never reach the threshold.

## Tuning note from the 0.5.0 session

Peak strength observed was `0.593`, giving refraction `0.1186` against the `0.20`
ceiling - heat never got near maximum during that test, so there is real headroom. If the
effect already looks right, consider lowering **Heat intensity** to around `0.14` so long
bursts do not overshoot.

Also: `bDebugLogging` now defaults to **off**. The 0.5.0 session produced a 1.4 MB log
from 2,136 ticks.
